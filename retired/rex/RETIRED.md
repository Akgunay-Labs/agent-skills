# Retired: `rex` orchestration skill

Retired 2026-10-25. Last release `rex/v0.1.0` (2026-10-10); the tag holds the
skill exactly as it shipped. This folder sits outside `skills/`, so
`scripts/check.py` and `scripts/link-skills.sh` ignore it. Do not link it back
as it is: its frontmatter still says `name: rex`.

## Why it was retired

1. **Name clash with the skill Rex ships.** Rex's Settings → Integrations →
   "Integrate with available agents" (and `rex skill setup`) installs its own
   skill named `rex` into `~/.claude/skills/rex` and `~/.agents/skills/rex`.
   Our symlinks occupied both paths, so Rex reported them as `foreign`, left
   them alone, and the settings pane showed "Couldn't update coding agents —
   could not finish for Claude Code, Codex, Pi". The hooks installed fine;
   only the skill step failed.
2. **A third of it duplicated what Rex now ships.** See the table below.
3. **It was not in use.** 31 run records, all from 2026-10-10/11 while it was
   being built and tested; none after.
4. **Policy: prefer what the vendor ships.** Rex is closed source. We cannot
   read its code or follow its internals, so every hand-written fact about Rex
   is a guess that silently goes stale. Rex's own skill is regenerated by the
   installed CLI on every use, so it never drifts from the build we run.

## What Rex ships (checked 2026-10-25, Rex `0.0.1792878257-g758aab`)

- `rex skill setup | status | remove | show`. Setup writes a small stub
  `SKILL.md` (frontmatter `metadata.rex-stub`) that tells the agent to run a
  `rex` subcommand and follow the guide it prints. The guide text lives in the
  CLI binary, so upgrading Rex updates it. `rex skill show` prints it.
- Session-start hooks for Claude Code (`~/.claude/settings.json`) and Codex
  (`~/.codex/hooks.json`) that tell the agent its `REX_SESSION` and
  `REX_BLOCK`. OpenCode and Pi get the skill only.
- Setup refuses to replace a `rex` skill it did not install (`foreign` /
  `conflict`); `--force` replaces it. Never use `--force` while a personal
  `rex` symlink exists: it would write through the link into this repository.

## Overlap: ours vs Rex's guide

| Topic | Ours (`v0.1.0`) | Rex's guide |
|---|---|---|
| Bind to your session and pane (`whoami`, `REX_*`, `ls --json`), full IDs over labels | §1 | yes |
| Raw commands: `run`, `split`, `wait`, `capture`, `send`, `send-key`, `close`, `--keep-open` | §6 + `references/targets-and-entry-paths.md` | yes, with recipes |
| Discovery: `--help`, `api list`, `api describe`, `block inspect`, docs | §7 | yes |
| Don't type into your own pane; check state before retrying a timed-out command | partly | yes |
| Control the Rex app (`-C CLIENT do …`) | no | yes |
| Launch, wait for, watch, send to, resume, review and cancel worker agents (`scripts/rex_assign.py`, run records) | yes | **no** |
| Mode A (process per assignment) vs Mode B (interactive worker) | yes | **no** |
| Executor → reviewer flow with a recorded verdict | yes | **no** |
| "What a signal proves" table; takeover detection; never answer a worker's permission dialog | yes | **no** |
| Codex quirks (`shell_environment_policy.inherit=all`, `--approve-for-me`); driving Rex from outside a pane | yes | **no** |

Rex's guide teaches an agent to use Rex. It says nothing about running other
agents inside Rex. Everything in the **no** rows is the only reason to come
back.

## Facts in `v0.1.0` known to be stale on 2026-10-25

- "Claude Code emits no status protocol": Claude Code 2.1.299 emits native
  OSC 7501 (`app=claude-code`) unless `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1`
  is set.
- Version pins (Rex `0.0.1791564903-g7abb0a`, Claude Code 2.1.296, Codex
  0.162.1) are several builds behind.
- `FIELD-NOTES.md` lists seven open issues from the first real run (no
  progress signal in Mode A, `Write` without `Edit`, unverifiable method
  claims, and more). None were fixed.

## If we come back to orchestration

Do these in order. Skipping step 1 or 2 is how this went wrong.

1. **Look for a shipped answer first.** Check the Rex changelog and the
   #feedback forum (an "agent lifecycle integration for external
   orchestrators" request was open in October 2026), `rex skill show`, and
   `rex api list`. Also check orchestration tools that already exist and
   are maintained by others, such as ACP-based runners. Write our own only
   for the gap that remains.
2. **Never reuse a vendor skill's name.** Name it `rex-orch` (or similar). After
   linking, `rex skill status` must still say `current` for every agent.
3. **Build on Rex's skill, don't restate it.** The new skill starts with "use
   the `rex` skill for CLI basics" and covers only the **no** rows above.
4. **Treat every Rex fact as observed, not known.** Pin the Rex build next to
   each claim, and re-verify on upgrade; there is no source to check against.
5. **Read `FIELD-NOTES.md` before writing code**, and fix or consciously drop
   each of its issues.

To restore the files: `git mv retired/rex skills/rex-orch`, change `name:` in
`SKILL.md` to `rex-orch`, rewrite the description, then follow the
`superpowers:writing-skills` workflow and `scripts/check.py` as for any new
skill.
